# Backend audit — 2026-10-23

Baseline `340c93e` plus this change, local PostgreSQL 16 (migrations 001–041), fictional data. Method: read the data layer and job runner against the known-gaps lists in the earlier audits, fuzz the router, and test what was changed.

## Probes that found nothing

- **Router fuzz:** 34 API families × junk path segments (non-UUIDs, null bytes, 5,000-character ids, SQL text), hostile query strings (negative and huge `limit`, bad cursors, array params), and malformed, huge (2 MB) and prototype-pollution bodies, as a signed-in organization member: **0 server errors** (5xx other than a deliberate 503). Ad hoc script, not committed.
- **Concurrency:** six parallel creates with one idempotency key return one load; six creates racing for one reference produce exactly one load and clean unique-violation rejections (the router answers 409 `DUPLICATE_REFERENCE`); the rate limiter admits exactly its quota under 25 parallel callers.
- **Restore:** a custom-format dump restores into a scratch database with identical row counts, the same migration version and the append-only audit trigger armed.

## Still missing (not fixed here, with reasons)

- **Validation ran before authorization** on some writes (document templates, drafts, prospects answered a malformed body with field errors to carrier managers and drivers). Fixed by ADR 0059: every API family now has a declared audience, checked before the body is read; outsiders get 404. The families marked `any` still rely on their handlers.
- **Session UI:** added on Account > Security (list, sign out one, sign out everywhere else), browser-tested.
- **Outbox has no consumer** (ADR 0049); rows accumulate. Nothing reads them, so a backlog count would be meaningless until an integration exists.
- **Retention and deletion policy** for documents, messages and audit logs needs legal review.
- **Live-provider verification, tracking observations, metrics and tracing** are unchanged; alerting now covers failures but there is no latency or error-rate metric.
- **Index choice was made from foreign keys and code reading, not from production query statistics.** Revisit with `pg_stat_statements` on real data; the new indexes are small and removable (rollback note in 041).
- **Restore drill is not in CI** because the runner's `pg_dump` version must match the service container; run it by hand monthly.
